# Rails 인증 이식 구현 계획 (C2)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 외부 auth 서비스 의존을 걷어내고 자체 JWT 인증으로 바꾼다 — 가입·로그인·회전·로그아웃과 `/users/me`.

**Architecture:** 정본(FastAPI)의 `app/auth/` 세 모듈(비밀번호·토큰·refresh 세션)을 Rails로 옮기고, 그 위에 `AuthController`와 Bearer 가드를 얹는다. refresh 회전은 사용자 행을 잠근 한 트랜잭션 안에서 일어나며, 이미 폐기된 세션으로 회전을 시도하면 그 사용자의 활성 세션을 **전부** 끊는다. 마지막에 `AuthServiceClient`·`AuthUser`와 WireMock 스텁을 지운다.

**Tech Stack:** Rails 8.1.2, PostgreSQL 18, `jwt` 3.2.0, `argon2` 2.3.3, Sidekiq + sidekiq-cron, RSpec, rswag, RuboCop, Brakeman

**Spec:** `docs/superpowers/specs/2026-09-04-contract-parity-design.md` — 단계 3 (§6)

**참조 구현 둘:**
- **정본** `template-python-fastapi` — `app/auth/{passwords,tokens,refresh_sessions,dependencies}.py`, `app/controllers/api/v1/{auth_controller,users_controller}.py`, `app/schemas/auth.py`, `app/serializers/auth_token_serializer.py`
- **B** `template-typescript-nestjs` — `src/app/auth/{password,tokens,refresh-session,current-user.guard}.ts`, `src/app/controllers/api/v1/auth.controller.ts`, `src/app/schemas/auth.schemas.ts`

**정본이 권위다.** B는 두 번째 관점으로만 쓴다 — C1에서 B가 정본과 갈린 자리가 여러 번 나왔다.

## Global Constraints

- **완료 조건은 하나다 — 같은 요청에 정본과 같은 문서가 나온다.**
- **검증 게이트는 넷이다.** 순서대로: `bundle exec rspec` → `COVERAGE_MINIMUM=0 bundle exec rails rswag:specs:swaggerize` + `git diff --exit-code -- swagger/v1/swagger.yaml` → `bundle exec brakeman --no-pager -q` → `bundle exec rubocop`.
- 커밋 메시지에 **`Co-Authored-By`도 AI 표기도 넣지 않는다.** 주석과 커밋 메시지는 한국어.
- **로그인의 순서는 계약이다** (스펙 §6.5). 이메일이 없어도 argon2 검증을 한 번 돌리고, 비밀번호를 먼저 검증한 뒤 활성 여부를 본다. 순서를 뒤집으면 응답 시간과 오류 코드가 계정 존재를 알려 준다.
- **정상 회전은 한 트랜잭션 안에서 일어난다.** 폐기와 생성이 갈라지면 로그인은 되는데 갱신은 안 되는 상태가 남는다.
- **재사용 감지는 그 사용자의 모든 세션을 끊는다** — 훔친 토큰이 쓰였다는 신호이므로 세션 하나가 아니다.
- 비밀번호는 12~128자, argon2. **bcrypt를 쓰지 않는다** — 72바이트에서 잘라내므로 73바이트부터 다른 두 비밀번호가 모두 로그인에 성공한다.
- refresh 토큰 저장 해시는 SHA-256이고 비교는 상수 시간이다. 토큰이 이미 고엔트로피라 느린 해시가 필요 없다.
- `JWT_SECRET_KEY`는 필수이고 UTF-8 기준 32바이트 이상. 누락하면 **변수 이름이 담긴 오류와 함께 시작에 실패한다** — 애플리케이션 코드에 암묵적 기본값을 두지 않는다.
- **`page[...]`·`filter[...]`·`sort` 같은 쿼리 파라미터를 auth 라우트에서 받지 않는다.** 기존 `jsonapi_query_mode` 기본값 `:none`이 그 역할을 한다.

## 실측해 둔 사실 — 다시 확인하지 않아도 된다

컨테이너에서 직접 돌려 확인했다.

- **`jwt` 3.2.0과 `argon2` 2.3.3이 이 이미지에서 빌드된다.** argon2는 네이티브 확장을 컴파일하며 `Dockerfile`의 bundle 단계에 `build-essential`이 있어 성공한다.
- **jwt 3.x API가 계획이 쓰는 모양 그대로 동작한다:**

```ruby
JWT.encode({ sub:, jti:, type:, iat:, exp:, iss:, aud: }, secret, "HS256")
JWT.decode(token, secret, true, {
  algorithm: "HS256",
  iss: issuer,  verify_iss: true,
  aud: audience, verify_aud: true,
  required_claims: %w[sub jti type iat exp iss aud]
})
```

- **argon2 API:** `Argon2::Password.create(raw)` / `Argon2::Password.verify_password(raw, hash)` — 맞는 비밀번호에 `true`, 틀린 비밀번호에 `false`.

## 스펙의 오류 하나 — 이 계획이 정정한다

**§6.9가 `app/auth/passwords.rb · tokens.rb · refresh_sessions.rb`라고 한다. 그 경로에 두면 안 된다.**

Rails는 `app/*` **각각을** Zeitwerk 루트로 등록한다(`paths.add "app", glob: "{*,*/concerns}"`). 따라서 `app/auth/passwords.rb`는 **최상위 `Passwords`**를 정의해야 하고, `Auth::Passwords`를 넣으면 `NameError`가 난다. 최상위 `Passwords`·`Tokens`·`RefreshSessions`는 이름이 너무 일반적이라 충돌을 부른다.

**C1에서 같은 문제를 이미 겪었고 실측으로 해결했다.** 스펙 §5.3이 `app/jsonapi/`라고 했는데 같은 이유로 성립하지 않아 `app/lib/jsonapi/`로 옮겼다. `app/lib`는 그 자체가 루트이므로 `app/lib/auth/passwords.rb` → `Auth::Passwords`가 설정 한 줄 없이 성립하고, SimpleCov의 `track_files "app/**/*.rb"`에도 걸린다.

**따라서 `app/lib/auth/`를 쓴다.** `app/controllers/concerns/jsonapi_authentication.rb`는 스펙대로 둔다 — 그 디렉터리는 루트이고 최상위 `JsonapiAuthentication`이 맞다.

- [ ] **Step 3: `app/lib/auth/passwords.rb`**

```ruby
# frozen_string_literal: true

module Auth
  # argon2 비밀번호 해시와 검증.
  #
  # bcrypt를 쓰지 않는 이유는 72바이트에서 잘라내기 때문이다. 계약상 비밀번호가
  # 12~128자이므로 bcrypt를 쓰면 73바이트부터 다른 두 비밀번호가 모두 로그인에
  # 성공하는 상태가 조용히 생긴다.
  module Passwords
    module_function

    def hash_password(raw)
      Argon2::Password.create(raw)
    end

    def verify_password(raw, stored_hash)
      Argon2::Password.verify_password(raw, stored_hash)
    rescue Argon2::ArgonHashFail, ArgumentError
      false
    end

    # 이메일이 없을 때도 검증을 한 번 돌리기 위한 해시다 — 스펙 6.5.
    # 즉시 반환하면 응답 시간이 "그 계정은 없다"를 알려 준다.
    def dummy_hash
      @dummy_hash ||= hash_password(SecureRandom.hex(32))
    end
  end
end
```

`rescue`가 잡는 예외 클래스가 실제로 무엇인지 **컨테이너에서 확인하라** — 손상된 해시 문자열을 넘겨 보고 실제로 나는 예외를 잡는다. 위 목록은 출발점이지 인벤토리가 아니다.

- [ ] **Step 4: 실패하는 토큰 테스트를 쓴다**

`spec/lib/auth/tokens_spec.rb`. 정본 `app/auth/tokens.py`의 `_typed_claims`가 **PyJWT가 열어 둔 것을 무엇으로 메우는지** 주석에 적어 뒀다 — 그 목록이 그대로 테스트 목록이다:

- 왕복: 발급한 access 토큰이 `expected_type: "access"`로 해석된다
- **`type`이 다르면 거부** — refresh 토큰을 `expected_type: "access"`로 해석하면 `InvalidToken`
- 서명 위조 → `InvalidToken`
- 만료 → `TokenExpired` (`InvalidToken`이 아니다 — 회전이 둘을 구분한다)
- `iss` 불일치, `aud` 불일치 → `InvalidToken`
- 필수 클레임 누락 → `InvalidToken`
- `sub`가 빈 문자열 → `InvalidToken`
- `jti`가 UUID로 파싱되지 않음 → `InvalidToken`
- `iat`/`exp`가 숫자가 아님(특히 `true`/`false`) → `InvalidToken`
- `decode_expired_refresh`는 만료만 통과시키고 나머지 검증은 그대로 한다
- `hash_refresh_token`이 SHA-256 hex이고, `refresh_token_matches?`가 상수 시간 비교다

**`aud`를 정확히 비교하라.** 정본 주석이 명시한다 — PyJWT는 `aud` **멤버십**만 보므로 정확히 같은지를 따로 봐야 한다. Ruby의 `jwt` 3.x가 어떻게 하는지 **실측하고**, 멤버십만 본다면 같은 보정을 넣는다.

- [ ] **Step 5: `app/lib/auth/tokens.rb`를 만든다**

claims는 `sub` · `jti` · `type` · `iat` · `exp` · `iss` · `aud` 일곱이다(스펙 §6.2). access와 refresh가 **같은 모양**이고 `type`만 다르다.

실측해 둔 API:

```ruby
JWT.encode(payload, secret, "HS256")
JWT.decode(token, secret, true, {
  algorithm: "HS256",
  iss: issuer,   verify_iss: true,
  aud: audience, verify_aud: true,
  required_claims: %w[sub jti type iat exp iss aud]
})
```

만료는 `JWT::ExpiredSignature`, 그 외 실패는 `JWT::DecodeError` 계열이다 — **실제 예외 클래스를 확인하고** 그것을 `TokenExpired` / `InvalidToken`으로 옮긴다.

`decode_expired_refresh`는 만료 검증만 끈다(`verify_expiration: false`) — **다른 검증은 그대로다.**

- [ ] **Step 1: 실패하는 테스트를 먼저 쓴다 — 여덟 갈래**

정본의 `rotate_refresh_session`과 `_load_verified_refresh_session`이 가르는 갈래가 그대로 테스트 목록이다.

1. **정상 회전** — 옛 세션에 `revoked_at`이 찍히고, 새 세션이 생기고, 옛 세션의 `replaced_by_id`가 새 세션 id를 가리킨다. 새 토큰 쌍이 나온다.
2. **재사용 감지** — 이미 `revoked_at`이 있는 세션으로 회전하면 **그 사용자의 활성 세션이 전부** `revoked_at`을 받고 401 `TOKEN_REVOKED`. *다른 사용자의 세션은 건드리지 않는다* — 이것도 단언하라.
3. **비활성 사용자** — 그 세션 하나만 폐기하고 403 `USER_INACTIVE`.
4. **만료 토큰** — 세션을 폐기하고 401 `TOKEN_EXPIRED`. 정본은 만료를 **두 단계로** 본다: JWT가 만료됐거나(`decode_expired_refresh`로 다시 읽어 claims를 얻는다) `refresh_session.expires_at <= now`이거나.
5. **서명이 깨진 토큰** — 401 `INVALID_TOKEN`. 세션을 건드리지 않는다.
6. **`jti`에 해당하는 세션이 없음** — 401 `INVALID_TOKEN`.
7. **세션은 있는데 `token_hash`가 안 맞음** (또는 `user_id`가 claims의 `sub`와 다름) — 401 `INVALID_TOKEN`.
8. **로그아웃은 멱등하다** — 두 번 불러도 둘 다 성공이고 `revoked_at`이 처음 값 그대로다.

**4번과 5번의 구분이 특히 중요하다.** 만료된 refresh 토큰은 서명이 유효하므로 세션을 찾아 폐기할 수 있다. 서명이 깨진 토큰은 어느 세션을 가리키는지 알 수 없으므로 아무것도 폐기하지 않는다. 이 둘을 한 갈래로 합치면 공격자가 아무 문자열이나 보내 세션을 폐기시킬 수 있다.

- [ ] **Step 2: 테스트가 실패하는 것을 확인한다**

Run: `bundle exec rspec spec/lib/auth/refresh_sessions_spec.rb`

- [ ] **Step 3: 구현한다**

정본의 구조를 그대로 따른다:

```text
load_verified_session(raw_token)
  1. claims 해석 — 만료면 decode_expired_refresh로 다시 읽고 token_was_expired = true
     해석 자체가 실패하면 INVALID_TOKEN
  2. claims.sub의 사용자를 잠근다 (SELECT ... FOR UPDATE)   없으면 INVALID_TOKEN
  3. claims.jti의 세션을 잠근다 (SELECT ... FOR UPDATE)
     없거나 user_id/token_hash가 안 맞으면 INVALID_TOKEN
  4. token_was_expired 이거나 session.expires_at <= now
       → revoked_at을 아직 없을 때만 채우고 TOKEN_EXPIRED
  5. (user, session, now) 반환

rotate(raw_token)
  세션에 revoked_at 있음 → 그 user의 활성 세션 전부 revoke, TOKEN_REVOKED
  user 비활성           → 그 세션만 revoke, USER_INACTIVE
  그 외                 → 옛 세션 revoke → 새 쌍 발급 → 옛 세션.replaced_by_id = 새 id
```

**잠금 순서를 지켜라 — 사용자 먼저, 세션 나중.** 두 요청이 반대 순서로 잠그면 교착한다.

트랜잭션은 **호출자가 소유한다**(정본이 `session.begin()`을 컨트롤러에 둔다). Rails에서는 `ActiveRecord::Base.transaction`을 컨트롤러에 두고 이 모듈은 그 안에서 돈다. 그래야 오류 갈래에서 **폐기가 커밋된다** — 재사용 감지가 세션을 끊었는데 예외로 롤백되면 감지가 없던 일이 된다.

**따라서 실패를 예외가 아니라 반환값(`Failure`)으로 표현한다.** 정본이 `RefreshSessionError`를 *반환*하는 이유가 그것이고, docstring에 "staged security state changes"라고 적혀 있다. 예외로 바꾸면 트랜잭션이 롤백되어 폐기가 사라진다. **이 결정을 코드 주석에 남겨라** — 다음 사람이 "왜 예외를 안 쓰지"라고 물을 자리다.

- [ ] **Step 4: 테스트가 통과하는 것을 확인한다**

- [ ] **Step 5: 뮤테이션으로 가드가 실재하는지 증명한다**

최소 넷을 깨 보고 각각 이름 있는 테스트가 실패하는지 본다:

1. 재사용 감지의 일괄 폐기를 그 세션 하나만 폐기하도록 좁힌다
2. `replaced_by_id` 대입을 지운다
3. 만료 판정에서 `token_was_expired`를 빼고 `expires_at`만 본다
4. 로그아웃의 멱등 대입을 무조건 대입으로 바꾼다

**깨지지 않는 것이 있으면 그 테스트가 공허한 것이다.** C1에서 픽스처가 두 순서를 우연히 같게 만들어 가드가 아무것도 지키지 못한 적이 **세 번** 있었다. 무엇을 돌렸고 무엇이 실패했는지 보고에 적는다.

- [ ] **Step 6: 전체 게이트 + 커밋**

커밋 메시지에 담을 것: 회전이 한 트랜잭션 안에서 일어나는 이유, 재사용 감지가 세션 하나가 아니라 전부를 끊는 이유, 그리고 **실패를 예외가 아니라 반환값으로 표현하는 이유**(예외로 올리면 트랜잭션이 롤백되어 방금 끊은 세션이 되살아난다).

| `POST /auth/logout` | `refreshTokens` | **204** (본문 없음) | — |

요청 속성: register·login은 `email`(≤254) + `password`(12~128). refresh·logout은 `refreshToken`.

`authTokens` 문서: `id`가 refresh jti, attributes `accessToken` · `refreshToken` · `tokenType`(`"Bearer"`) · `expiresIn` · `refreshExpiresIn`. **self 링크가 없다**(정본의 `resource_path = None`).

오류 갈래:

- 이메일 중복 → **409 `EMAIL_ALREADY_REGISTERED`**
- 잘못된 자격증명 → 401 `INVALID_CREDENTIALS`
- 로그인 시 비활성 사용자 → 403 `USER_INACTIVE`
- `data.type`이 다름 → 기존 `TYPE_MISMATCH`
- 비밀번호 11자 / 129자 → **기존 write 라우트와 같은 코드인지 실측 확인** 후 그 값으로 고정

**로그인 순서 테스트 두 개를 반드시 쓴다** (스펙 §6.5):

1. 존재하지 않는 이메일과, 존재하는 이메일 + 틀린 비밀번호가 **같은 코드**(`INVALID_CREDENTIALS`)를 낸다
2. **비활성 사용자에게 틀린 비밀번호**를 보내면 `USER_INACTIVE`가 아니라 `INVALID_CREDENTIALS`가 나온다

**2번이 순서 계약의 진짜 가드다.** 1번만으로는 dummy 해시 검증이 빠져도 통과한다 — 두 경로 모두 `INVALID_CREDENTIALS`를 내기 때문이다. 2번은 "활성 여부를 비밀번호보다 먼저 보면" 깨진다.

**지금 `jsonapi_errors.rb`가 그 예외를 일괄로 `RESOURCE_CONFLICT`에 매핑한다.** `AuthController`가 가입 경로에서 **먼저 잡아** `EMAIL_ALREADY_REGISTERED`로 바꾼다. **제약 이름을 확인해 이메일 유니크 위반일 때만** 바꾸고 그 외는 그대로 올린다 — 정본의 `_integrity_constraint_name`이 그렇게 한다. 무조건 바꾸면 다른 유니크 위반이 "이메일 중복"으로 보고된다.

## 완료 조건

네 게이트가 전부 통과하고, 아래가 모두 참이다.

- `POST /api/v1/auth/register`가 201과 `Location: /api/v1/users/me`를 내고 `users` 문서를 반환한다.
- 같은 이메일로 다시 가입하면 409 `EMAIL_ALREADY_REGISTERED`다.
- `POST /api/v1/auth/login`이 `authTokens` 문서를 낸다 — `accessToken` · `refreshToken` · `tokenType` · `expiresIn` · `refreshExpiresIn`.
- **존재하지 않는 이메일과 틀린 비밀번호가 같은 코드를 낸다.**
- **비활성 사용자에게 틀린 비밀번호를 보내면 `INVALID_CREDENTIALS`다** — `USER_INACTIVE`가 아니다.
- `POST /api/v1/auth/refresh`가 새 쌍을 내고, 옛 세션이 폐기되며, 옛 세션의 `replaced_by_id`가 새 세션을 가리킨다.
- **이미 폐기된 세션으로 회전하면 그 사용자의 활성 세션이 전부 폐기되고 401 `TOKEN_REVOKED`다.**
- 만료된 refresh 토큰은 401 `TOKEN_EXPIRED`, 서명이 깨진 토큰은 401 `INVALID_TOKEN`이고 **후자는 아무 세션도 폐기하지 않는다.**
- `POST /api/v1/auth/logout`이 204이고 **멱등하다.**
- `GET /api/v1/users/me`가 Bearer 토큰으로 200을 내고, 헤더가 없으면 401 `AUTHENTICATION_REQUIRED` + `source.header`를 낸다.
- **refresh 토큰을 access 자리에 넣으면 401 `INVALID_TOKEN`이다.**
- Example 쓰기가 Bearer 인증을 요구한다.
- `AuthServiceClient` · `AuthUser` · `AUTH_SERVICE_URL` · auth-stub의 잔재가 **0건**이다.
- 오류 카탈로그가 24개다 — 6개 추가, 2개 제거.
- 정리 job이 보존 기간이 지난 만료 세션만 지운다.

**마지막 검증은 정본과의 응답 대조다.** C1과 같은 이유로 자동화 스크립트는 만들지 않는다 — 두 스택을 동시에 띄워야 하므로 Rails 저장소가 FastAPI의 부팅 방법·포트·시드를 알아야 하고, 그 도구의 자연스러운 소유자는 3-백엔드 매트릭스 E2E를 가진 쪽이다.

**다만 C1에서 미룬 비용이 실측됐다는 사실을 함께 넘긴다:** 정본을 나란히 읽으면 5분에 잡히는 차이 두 건이 **다섯 번의 태스크 리뷰를 통과했다.** 그래서 이 계획의 모든 태스크가 "정본을 직접 읽어라"로 시작한다.
